# צינור איסוף הנתונים

כל הנתונים שהאתר מציג נוצרים כאן, בזמן בנייה, ונשמרים כקבצים סטטיים תחת `data/processed`.
האתר המפורסם אינו מבצע שום קריאת רשת כדי להציג נתונים.

## הרצה

```bash
npm run data:refresh          # כל השלבים, בסדר הנכון
```

או שלב-שלב:

```bash
npm run data:collect-sources    # קטלוג המקורות + ניסיון אחזור בפועל
npm run data:normalize-budget   # נתוני תקציב וביצוע
npm run data:usage-breakdown    # סיווג כלכלי רשמי (סוגי שימוש) ברמת התקנות
npm run data:collect-activities # פריטי פעילות פומבית
npm run data:classify-topics    # סיווג נושאים דטרמיניסטי
npm run data:classify-themes    # החלת הסיווג התמטי (LLM בזמן בנייה, קובץ מבוקר)
npm run data:build              # הרכבת ministries / coverage / methodology / CSV
npm run data:validate           # שער איכות — נכשל = לא מפרסמים
npm run data:report             # data/processed/DATA-REPORT.md
```

מאחורי proxy, הריצו כך כדי ש-`fetch` יכבד את `HTTPS_PROXY`
(נדרש Node ‎22.21 ומעלה, והמשתנה חייב להיות מוגדר לפני עליית התהליך):

```bash
NODE_USE_ENV_PROXY=1 npm run data:refresh
```

## אילו מקורות נאספים

סדר העדיפות קבוע, ומיושם בקוד:

| עדיפות | מקור                                      | לְמה משמש                       |
| ------ | ----------------------------------------- | ------------------------------- |
| 1      | Gov.il — עמודי נושא ודוחות ביצוע תקציב    | ביצוע ואומדנים, פרסומים רשמיים  |
| 2      | data.gov.il — קטלוג ה-CKAN                | מאגרי נתונים פתוחים             |
| 3      | משרד האוצר — החשב הכללי, אגף התקציבים     | ביצוע תקציב מפורט               |
| 4      | אתר הכנסת — ספר התקציב ומרכז המחקר והמידע | הצעות תקציב ודברי הסבר, ניתוחים |
| 5      | מבקר המדינה                               | דוחות ביצוע וביקורת             |
| 6      | מפתח התקציב (obudget) — **שכבת עזר בלבד** | זיהוי קודי תקציב, אימות משני    |

מפתח התקציב מסומן תמיד כ-`secondary_helper`, ונתון שמגיע ממנו לא מסומן לעולם כ-`final`.

## מה אוטומטי ומה ידני

**אוטומטי**

- אחזור כל URL בקטלוג, כולל רישום כל ניסיון.
- סיווג מקור: מפרסם, סוג, שנות תקציב, מיפוי למשרד — לפי כללים דטרמיניסטיים על ה-URL והכותרת
  (`scripts/lib/classify-source.ts`).
- סיווג נושאים לפי מילון מילות מפתח (`scripts/lib/topic-matching.ts`).
- חישוב שינוי תקציב, שיעור ביצוע ואגרגציות.
- ולידציה מלאה וייצוא CSV.

**ידני ומוצהר** — כל אחד מהם הוא קובץ שאפשר לבקר:

- `data/raw/search-discovery/*.json` — תוצאות הגילוי הגולמיות: כותרת ו-URL בדיוק כפי שהוחזרו.
- `data/raw/seeds/ministries.seed.json` — אילו משרדים נכללים, ומה הראיה לשם ולקוד התקציבי של כל אחד.
- `data/raw/seeds/topics.seed.json` — טקסונומיית הנושאים ומילות המפתח.
- `data/raw/seeds/topic-overrides.json` — שיוכי נושא ידניים לפריטים שאינם חד-משמעיים.

## כללי אתיקה ותפעול

מיושמים ב-`scripts/lib/http.ts`:

- **User-Agent מזהה** — מפעיל מקור יכול לראות מי פונה אליו ולאיזו מטרה.
- **timeout** של 30 שניות לכל בקשה.
- **retry מתון** — עד 3 ניסיונות, backoff של 1 ואז 3 שניות, ורק עבור כשל חולף.
  שגיאת 4xx (למעט 429) ודחיית מדיניות רשת אינן חוזרות — הן דטרמיניסטיות.
- **כיבוד קצב** — לפחות 1.2 שניות בין בקשות לאותו מתחם.
- **cache מקומי** תחת `data/.cache` (לא ב-git), כדי שהרצה חוזרת לא תכה שוב במקורות.
- **רישום שגיאות מסודר** — כל ניסיון נכתב ל-`data/raw/collection-log/`, כולל כשלונות.

אין scraping אגרסיבי, אין עקיפת הרשאות, אין CAPTCHA, אין התחברות פרטית, ואין מקורות שאינם פומביים.

## מגבלות גישה ידועות

- **PDF ו-Excel לא מנותחים.** ספר התקציב ודוחות הביצוע מתפרסמים כ-PDF/XLSX. חילוץ טבלאות
  מפריסת PDF אינו אמין, ולכן הוא **לא** מבוצע: המקור נשמר בקטלוג עם קישור, הכישלון מתועד,
  והנתון נשאר חסר. עדיף נתון חסר על נתון מנוחש.
- **מבנה ה-API של gov.il אינו מתועד פומבית** ועשוי להשתנות. `collect-activities` מאמת את מבנה
  התשובה לפני שימוש; מבנה שאינו מזוהה נרשם כ-`parse_error` ואינו מייצר רשומות.
- **גרסת הנתונים הנוכחית נאספה בסביבה עם allowlist ליציאה לרשת** שאינו כולל את מתחמי המקורות
  הרשמיים. כל הבקשות נענו ב-HTTP 403 עם ההודעה `Host not in allowlist`, ולכן קוטלגו 50 מקורות
  אמיתיים אך לא חולץ מהם אף נתון. היומן המלא: `data/raw/collection-log/`.
  הרצה מסביבה עם גישה רגילה תאכלס את הנתונים ללא שינוי קוד.

## איך מוסיפים משרד או מקור

1. הריצו חיפוש ומצאו מקור רשמי. הוסיפו את הכותרת וה-URL **בדיוק** כפי שהוחזרו, לקובץ גילוי
   חדש תחת `data/raw/search-discovery/`.
2. אם מדובר במשרד חדש — הוסיפו רשומה ל-`ministries.seed.json`, כולל `nameEvidence` שמצביע
   על המקור שמבסס את שם המשרד. משרד ללא ראיה לשם אינו נכנס למאגר.
3. אם נדרש כלל מיפוי חדש (למשל תבנית שם קובץ של ספר התקציב) — הוסיפו אותו
   ל-`scripts/lib/classify-source.ts`. הכלל נשמר בשדה `mappingRule` של כל מקור, כדי שאפשר יהיה
   לבקר אותו.
4. הריצו `npm run data:refresh`.
5. בדקו את `data/processed/DATA-REPORT.md` ואת ה-diff ב-`data/processed/`.

## איך מאמתים לפני פרסום

```bash
npm run data:validate   # 30 בדיקות: סכמות, כפילויות, תאריכים, סכומים, היררכיה, כיסוי
npm test                # בדיקות יחידה + בדיקות תקינות מול קובצי הנתונים שנשלחים לאתר
npm run build           # typecheck + build סטטי
npx playwright test     # smoke על האתר הבנוי
```

`data:validate` מחזיר קוד יציאה שונה מאפס בכל כשל, ו-`deploy-pages.yml` תלוי בו — כלומר
נתונים שאינם עוברים ולידציה לא מתפרסמים.

לפני שמאמינים למספר חדש, בדקו שלושה דברים ידנית:

1. ה-`sourceUrl` נפתח ומראה את המספר.
2. ה-`dataStatus` מתאים למה שהמקור באמת אומר (`final` רק ממקור סופי ומזוהה).
3. אין כפל ספירה: אם נוספו גם סעיף הורה וגם סעיפי בנים, רק אחת מהרמות אמורה להיסכם.

## אידמפוטנטיות

הכתיבה ל-JSON דטרמיניסטית: סדר מפתחות קבוע, הזחה של שני רווחים, שורת סיום אחת, ומיון לפי
מזהה. הרצה חוזרת על אותם קלטים מייצרת קובץ זהה ברמת הבתים, ולכן `git diff` ריק — וכל diff
שכן מופיע מייצג שינוי אמיתי במקור.
